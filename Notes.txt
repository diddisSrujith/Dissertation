The implementation process demonstrated that etymology extraction is considerably more complex than standard text extraction tasks due to the semi-structured and historically layered nature of dictionary etymologies. While regex approaches provided useful high-precision preprocessing, scalability limitations motivated the exploration of transformer and LLM-based methods. The challenges encountered throughout development significantly influenced the final hybrid methodology proposed in this dissertation.

Key Problems Encountered and Solutions Implemented
1. Hardcoded Language List
Problem

The initial system relied on a manually hardcoded list of languages:

languages = [
    "Old Frisian",
    "Old Dutch",
    ...
]

This caused several issues:

poor scalability,
inability to generalize to unseen etymologies,
difficult maintenance,
limited language coverage.
Solution

A separate language resource pipeline was introduced:

languages.json
generated from Wiktionary language data
language_families.json
manually curated supplementary ontology for:
proto-languages,
language families,
OED-specific historical labels

A dedicated loader module (language_loader.py) was added to:

merge resources,
deduplicate entries,
prioritize family names,
sort longest-first for regex safety.
Outcome

The parser became:

scalable,
reusable,
ontology-driven,
easier to maintain and extend.
2. Missing Proto-Languages and Language Families
Problem

Wiktionary-exported language data did not include many important etymological categories such as:

Indo-European,
Germanic,
Proto-Germanic,
Proto-Indo-European.

As a result:

ancestor extraction failed,
root hierarchy disappeared,
main graph structure became incomplete.
Solution

A supplementary ontology file:

language_families.json

was introduced.

This explicitly modeled:

language families,
proto-languages,
historical scholarly categories.
Outcome

The system successfully restored:

Indo-European → Germanic → descendant branches

and improved linguistic correctness.

3. Regex Overmatching and Substring Collisions
Problem

When scaling from a small hardcoded list to thousands of language names, regex alternation began causing collisions such as:

German matching inside Germanic.

This produced:

incorrect relations,
unstable graph topology,
unexpected extraction behavior.
Solution

Language names were:

sorted longest-first,
matched using token boundaries:
language_pattern = r"\b(?:{})\b".format(...)
Outcome

The parser became more stable and resistant to partial lexical matches.

4. Root Detection Instability
Problem

The original parser only detected roots using:

inherited from

However, OED etymologies use multiple formulations:

borrowed from,
derived from,
adopted from,
inherited from.
Solution

Root extraction was generalized:

(?:inherited|borrowed|derived|adopted)\s+from
Outcome

The system became compatible with a wider variety of OED etymology structures.

5. Noise Tokens and Descriptor Interference
Problem

OED entries frequently contain:

stylistic labels,
historical descriptors,
register markers.

Examples:

(poetic and rare)
regional
archaic
obsolete

These interfered with extraction logic.

Solution

A lightweight normalization layer was introduced to remove:

parenthesized descriptors,
inline stylistic markers,
semantic noise tokens.
Outcome

Extraction accuracy improved while preserving linguistic content.

6. Confusion Between Descendant Chains and Parallel Cognates
Problem

Initially, all relationships were treated similarly, even though:

genealogical descent,
cognate similarity

represent different linguistic phenomena.

This produced semantically incorrect graph structures.

Solution

The system was split into:

regex_extractor.py
genealogical/descendant relationships
parallel_extractor.py
parallel cognate relationships

Separate JSON outputs were generated:

data.json
parallel.json
Outcome

The visualization now correctly distinguishes:

inheritance trees,
parallel cognate relationships.
7. Regex Fragility with Large Ontologies
Problem

Scaling from a small language list to thousands of entries changed:

regex matching order,
extraction ordering,
graph root selection behavior.

The extraction pipeline became highly sensitive to unintended matches.

Solution

Instead of rewriting the parser:

ontology management was separated,
relation debugging was introduced,
matching priority was controlled through sorting and ontology layering.
Outcome

The parser remained structurally stable while becoming scalable.

8. Tree Construction Ambiguity
Problem

Graph roots were inferred using:

all_parents - children_set

Unexpected relations could change:

root selection,
overall tree topology.
Solution

Relation extraction was stabilized through:

ontology cleanup,
regex normalization,
elimination of false-positive matches.
Outcome

The correct etymological hierarchy emerged consistently.

9. Lack of Modular Architecture
Problem

Initially, all logic existed in a single script:

extraction,
ontology,
graph construction,
visualization.

This reduced maintainability.

Solution

The project was modularized into:

ontology layer,
extraction layer,
graph construction layer,
visualization layer.
Outcome

The final system became significantly more extensible and research-oriented.

Final System Architecture
1.Data Layer

3.Extraction Layer

The project evolved from:

into:

Step 1 — Preprocessing

The parser first combines the origin and etymology into a single text block.

Origin: Germanic

Etymology:
Inherited from Proto-Germanic...

↓

The text is cleaned using preprocess_text().

The preprocessing stage normalises

whitespace
punctuation
line breaks
formatting inconsistencies

This provides a consistent input for pattern matching.

Step 2 — Dynamic Language Pattern Generation

Instead of hardcoding languages, the parser loads every language from

languages.json

Example

Old English
Middle English
Proto-Germanic
Latin
Old Norse
Old Frisian
...

These are converted into one large regular expression

Old\ English|Middle\ English|
Proto\-Germanic|Latin|...

This allows the parser to recognise any supported language without manually updating regex rules.

Step 3 — Root Language Detection

The parser identifies the root language using several expressions.

P1
Inherited from <Language>
Borrowed from <Language>
Derived from <Language>
Borrowing from <Language>
Adopted from <Language>

Example

Inherited from Proto-Germanic

↓

Root = Proto-Germanic
P2
Common <Language>

Example

Common Germanic

↓

Root = Germanic
P3
same <Language> base

Example

same Proto-Indo-European base

↓

Root = Proto-Indo-European
P4
< Language

Example

< Proto-Indo-European

↓

Root = Proto-Indo-European

The parser searches for

The parser removes sections that are not part of the primary ancestry.

Parsing stops before phrases such as

Before creating nodes, lexical forms are cleaned.

The parser also removes descriptors such as

(regional)

(rare)

(plural)

(feminine)

Every language–word pair outside descendant blocks becomes an ancestor of the root language.

Old Frisian

 ancestor

Sometimes descendant chains are disconnected.

Example

↓

The parser automatically adds

      │

Step 11 — Duplicate Removal

Every extracted edge passes through

add_relation()

Duplicate edges are ignored.

Step 12 — Graph Construction

The parser finally produces three relation types.

These are written to

relations.json

and passed to

tree_builder.py

which constructs the final JSON tree used for visualization.
